Why Docker?

Docker packages your app and its dependencies into an isolated "container" — like a mini virtual machine. This means your app runs the same way on every computer, and Windows' Smart App Control policy cannot block code running inside containers.

🍃
Why MongoDB (NoSQL)?

The football API returns data as JSON (nested objects). MongoDB stores JSON documents natively — no need to design rigid tables like in SQL. You just save what you receive.

docker-compose.yml

Tells Docker what containers to create and how they connect to each other

Purpose

Docker Compose is a tool that lets you define and run multiple containers with one command (docker-compose up). Instead of starting MongoDB and your app separately, this file describes both and Docker handles everything.

version: "3.8"

services:

  mongodb:
    image: mongo:7
    container_name: football_db
    ports:
      - "27017:27017"
    volumes:
      - mongo_data:/data/db

  app:
    build: .
    container_name: football_app
    ports:
      - "8501:8501"
    depends_on:
      - mongodb
    environment:
      - MONGO_URI=mongodb://mongodb:27017
      - FOOTBALL_API_TOKEN=${FOOTBALL_API_TOKEN}
    volumes:
      - .:/app

volumes:
  mongo_data:
LineCodeExplanation
1version: "3.8"Specifies which version of the docker-compose file format to use. Version 3.8 supports all modern Docker features. Think of it like saying "use Word 2019 format" for a document.
3services:This keyword opens the section where you list all the containers you want Docker to run. Each indented item below is one container (service).
5mongodb:The name we give to our first container. We can use this name later to refer to this container from other containers (like an internal hostname).
6image: mongo:7Tells Docker to download and use the official MongoDB image version 7 from Docker Hub (Docker's app store). You don't need to install MongoDB — Docker downloads and runs it for you.
7container_name: football_dbThe friendly name shown in Docker Desktop. Without this, Docker generates a random name like "loving_newton".
9"27017:27017"Port mapping: format is "your-machine-port:container-port". This makes MongoDB accessible from outside the container. 27017 is MongoDB's default port — like how 80 is the default for websites.
11mongo_data:/data/dbConnects a persistent "volume" (a special Docker storage area) to the folder inside the container where MongoDB saves its data. Without this, ALL your data disappears every time you stop the container.
14build: .Instead of using a pre-made image, Docker should BUILD an image using the Dockerfile in the current directory (the dot "." means "here"). This is how your Python code gets containerized.
17"8501:8501"Exposes Streamlit's port. When you open localhost:8501 in your browser, Docker forwards that to port 8501 inside the app container where Streamlit is listening.
19depends_on: mongodbTells Docker: "don't start the app container until MongoDB is running." Without this, the app might try to connect to the database before it's ready and crash.
21MONGO_URI=mongodb://mongodb:27017Sets an environment variable inside the app container. Crucially: the hostname is "mongodb" (the service name), NOT "localhost". Inside Docker, containers use each other's service names as hostnames.
22${FOOTBALL_API_TOKEN}The ${} syntax reads a variable from your .env file on your machine and passes its value into the container. This keeps your secret token out of the code.
24.:/appMounts your local project folder into the container at /app. This means any file you edit on your machine is instantly available inside the container — no need to rebuild when you change code.
27mongo_data:Declares the named volume used above. Docker creates and manages this storage area. Data stored here survives container restarts and deletions.

Dockerfile

Blueprint for building the Python application container image

Purpose

A Dockerfile is a recipe. It tells Docker how to build a container image for your app — starting from a base Python installation, adding your code and libraries. Think of it like a setup guide that Docker follows automatically.

FROM python:3.12-slim

WORKDIR /app

COPY requirements.txt .

RUN pip install -r requirements.txt

COPY . .

EXPOSE 8501

CMD ["python", "-m", "streamlit", "run", "app/app.py", "--server.address=0.0.0.0"]
LineCodeExplanation
1FROM python:3.12-slimEvery Dockerfile starts with FROM — it picks the base image to build on top of. "python:3.12-slim" is an official Docker image with Python 3.12 already installed. "slim" means it's a minimal Linux installation (smaller = faster to download and more secure).
3WORKDIR /appSets the working directory inside the container. All subsequent commands (COPY, RUN, CMD) happen relative to this folder. If /app doesn't exist, Docker creates it. It's like doing "cd /app" but permanent for the container.
5COPY requirements.txt .Copies the requirements.txt file from your machine into the container's current directory (/app). The dot "." at the end means "copy to the current WORKDIR". We copy this BEFORE the rest of the code for a smart reason — see tip below.
7RUN pip install -r requirements.txtRUN executes a shell command during the build process. This installs all Python libraries listed in requirements.txt. This step is cached by Docker — if requirements.txt doesn't change, Docker reuses the cached result instead of re-downloading everything.
9COPY . .Copies everything from your project folder into /app in the container. The first dot is "source" (your machine), the second is "destination" (container). This happens AFTER pip install so that changing your Python code doesn't invalidate the pip cache.
11EXPOSE 8501Documents that this container listens on port 8501. It's informational — the actual port binding is done in docker-compose.yml. Think of it like labeling a door "entrance".
13CMD [...]The command that runs when the container starts. CMD uses JSON array format. This is equivalent to running: python -m streamlit run app/app.py --server.address=0.0.0.0. The --server.address=0.0.0.0 flag is critical — without it Streamlit only accepts connections from inside the container and you can't reach it from your browser.
💡
Why copy requirements.txt before the rest of the code?

Docker builds images in layers and caches each layer. If you change a Python file, Docker only rebuilds from that changed layer onwards. By copying requirements.txt first and running pip install before copying your code, Docker can reuse the "pip install" layer (which takes ~2 minutes) even when you change your Python files. This makes rebuilds much faster.

fetcher/fetcher.py

Downloads live data from football-data.org and saves it to MongoDB

Purpose

This file is the data collector. It makes HTTP requests to the football API (like a browser loading a webpage, but in code), reads the JSON response, and stores it in MongoDB. Think of it as a robot that reads a football website every morning and saves everything to your database.

import os
import requests
from pymongo import MongoClient
from dotenv import load_dotenv

load_dotenv()

API_TOKEN = os.getenv("FOOTBALL_API_TOKEN")
MONGO_URI = os.getenv("MONGO_URI", "mongodb://localhost:27017")
BASE_URL = "https://api.football-data.org/v4"
HEADERS = {"X-Auth-Token": API_TOKEN}

client = MongoClient(MONGO_URI)
db = client["football_analytics"]

def fetch_standings():
    response = requests.get(f"{BASE_URL}/competitions/PL/standings", headers=HEADERS)
    response.raise_for_status()
    data = response.json()
    standings = data["standings"][0]["table"]
    db.standings.drop()
    db.standings.insert_many(standings)
    print(f"Saved {len(standings)} team standings")

def fetch_matches():
    response = requests.get(f"{BASE_URL}/competitions/PL/matches", headers=HEADERS)
    response.raise_for_status()
    matches = response.json()["matches"]
    db.matches.drop()
    db.matches.insert_many(matches)
    print(f"Saved {len(matches)} matches")

def fetch_scorers():
    response = requests.get(f"{BASE_URL}/competitions/PL/scorers?limit=20", headers=HEADERS)
    response.raise_for_status()
    scorers = response.json()["scorers"]
    db.scorers.drop()
    db.scorers.insert_many(scorers)
    print(f"Saved {len(scorers)} scorers")

def fetch_all():
    fetch_standings()
    fetch_matches()
    fetch_scorers()

if __name__ == "__main__":
    fetch_all()

1import osos is a built-in Python module (no installation needed). We use it specifically for os.getenv() which reads environment variables — values set in your .env file or in the system.
2import requestsThe requests library (installed via pip) makes HTTP calls simple. An HTTP call is what happens when your browser loads a webpage — we do the same thing but from Python code to get data from the API.

fetch_standings() function

LineCodeExplanation
—def fetch_standings():"def" defines a new function. Functions are reusable blocks of code with a name. "fetch_standings" describes what this function does — good naming makes code readable. The parentheses () hold parameters (inputs) — this function needs none.
—requests.get(url, headers=...)Sends an HTTP GET request to the URL — exactly like your browser loading a page. The "headers" parameter attaches our authentication token. Returns a "response" object containing the server's reply.
—f"{BASE_URL}/competitions/PL/standings"An f-string (formatted string). The f prefix lets you embed variables inside {} directly in the string. This produces: "https://api.football-data.org/v4/competitions/PL/standings". "PL" is the Premier League's competition code.
—response.raise_for_status()Checks if the request succeeded. HTTP responses include a status code: 200=OK, 401=wrong token, 429=too many requests, 500=server error. raise_for_status() throws an exception (stops the program with an error message) if the status isn't 200. Better to crash loudly than fail silently.
—response.json()The API returns data as a JSON string (text). .json() parses that string into a Python dictionary. After this call, "data" is a normal Python dict you can work with using data["key"] syntax.
—data["standings"][0]["table"]Navigates the nested JSON structure. The API returns three standing types: overall [0], home [1], away [2]. We want [0] (overall). The "table" key inside that gives us the list of 20 team rows.
—db.standings.drop()Deletes all documents in the "standings" collection. We do this before re-inserting to avoid duplicates. Each time we fetch, we want fresh data, not the old data plus the new data combined.
—db.standings.insert_many(standings)"standings" is now a Python list of 20 dicts. insert_many() saves all of them to MongoDB in one operation. MongoDB assigns each document a unique _id automatically.
📘
What is JSON?

JSON (JavaScript Object Notation) is a text format for structured data. It looks like Python dictionaries and lists. Example: {"team": {"name": "Arsenal"}, "points": 45, "won": 14}. APIs return JSON because it's easy to send as text over the internet and easy to parse in any programming language.

if __name__ == "__main__"

LineCodeExplanation
—if __name__ == "__main__":Python sets a special variable __name__ to "__main__" when a file is run directly (python fetcher.py). When another file imports from fetcher.py, __name__ is set to "fetcher" instead. This block only runs in the first case, preventing fetch_all() from running accidentally when the file is imported.

predictor/predictor.py

Monte Carlo simulation — estimates each team's probability of winning the league

What is Monte Carlo Simulation?

Named after the famous casino in Monaco, Monte Carlo simulation uses random sampling to solve problems. We can't know who will win each future match — but we can estimate probabilities and simulate the rest of the season thousands of times. If Arsenal wins in 6,200 out of 10,000 simulated seasons → Arsenal has a 62% chance of winning the title.

SIMULATIONS = 10_000

def get_team_strengths():
    standings = list(db.standings.find({}, {"_id": 0}))
    strengths = {}
    for row in standings:
        team_name = row["team"]["name"]
        played    = row["playedGames"]
        points    = row["points"]
        gd        = row["goalDifference"]
        ppg   = points / played if played else 0.0
        gdpg  = gd / played if played else 0.0
        form_str     = row.get("form") or ""
        form_results = [r for r in form_str.split(",") if r]
        form_pts = sum(3 if r=="W" else 1 if r=="D" else 0 for r in form_results)
        form_avg = form_pts / max(len(form_results), 1)
        strengths[team_name] = (ppg*0.6) + (gdpg*0.2) + (form_avg*0.2)
    return strengths

def simulate_match(home_strength, away_strength):
    home_adj = home_strength + 0.3
    total    = home_adj + away_strength
    if total == 0:
        return random.choice(["H", "D", "A"])
    p_home = (home_adj / total) * 0.75
    p_away = (away_strength / total) * 0.75
    p_draw = 1.0 - p_home - p_away
    r = random.random()
    if   r < p_home:              return "H"
    elif r < p_home + p_draw:    return "D"
    else:                          return "A"

get_team_strengths() — calculating how good each team is

LineCodeExplanation
—SIMULATIONS = 10_000A constant at the top of the file. 10,000 simulations gives ~1% accuracy (good enough). The underscore _ in 10_000 is a Python readability trick — completely ignored by Python, same as writing 10000. Like writing 10,000 with a comma.
—db.standings.find({}, {"_id": 0})Queries MongoDB. find({}) with empty filter returns ALL documents. The second argument {"_id": 0} is a "projection" — it tells MongoDB which fields to return. 0 means exclude, 1 means include. We exclude _id because MongoDB's internal ID is an object Python can't easily print.
—list(...)MongoDB's find() returns a "cursor" — a lazy iterator that fetches results one by one. Wrapping it in list() forces Python to fetch all results at once into a regular Python list we can loop over multiple times.
—ppg = points / played if played else 0.0A conditional expression (ternary operator). Reads as: "if played is not zero, calculate points/played; otherwise use 0.0". This prevents a ZeroDivisionError at the start of the season when teams have played 0 games.
—row.get("form") or "".get("form") safely reads the "form" key — returns None if the key doesn't exist, instead of crashing. The "or ''" part means: if .get() returned None (or any falsy value), use an empty string instead.
—[r for r in form_str.split(",") if r]A list comprehension — a compact way to build a list. split(",") turns "W,D,L,W,W" into ["W","D","L","W","W"]. The "if r" filters out empty strings that could appear from trailing commas. Result: a clean list of single-character results.
—sum(3 if r=="W" else 1 if r=="D" else 0 for r in form_results)A generator expression inside sum(). For each result r, it produces a number (3, 1, or 0). sum() adds them all. This is the same as a for loop that accumulates a total, written in one line.
—(ppg*0.6) + (gdpg*0.2) + (form_avg*0.2)The strength formula. We weight three factors: points per game (60% — most reliable indicator), goal difference per game (20% — shows quality beyond just results), recent form (20% — captures current momentum). Weights sum to 1.0.

simulate_match() — simulating one game outcome

LineCodeExplanation
—home_adj = home_strength + 0.3Home advantage. In the Premier League, home teams win ~46% of games vs ~29% for away teams. Adding 0.3 to the home team's strength models this statistical reality.
—total = home_adj + away_strengthThe sum of both teams' adjusted strengths. We use this to calculate each team's share of the total strength, which becomes their win probability.
—p_home = (home_adj / total) * 0.75Home win probability. We divide by total to get the team's proportion (e.g., 0.55), then multiply by 0.75 to leave 25% for draws. In real football ~25% of matches end in draws.
—p_draw = 1.0 - p_home - p_awayDraw probability is whatever's left after assigning home and away win probabilities. Since all probabilities must sum to 1.0 (something has to happen), the draw probability fills the gap.
—r = random.random()Generates a random float between 0.0 and 1.0. This is our "dice roll". If p_home=0.5, then about 50% of the time r will be less than 0.5, meaning home team wins about 50% of simulations.
—if r < p_home: return "H"If our random number falls in the home team's probability range, home wins. elif r < p_home + p_draw catches the draw range. Everything else is an away win. Together these three cases cover the full 0.0–1.0 range.

scheduler/scheduler.py

Runs the fetcher and predictor automatically every morning at 6am

Purpose

Instead of manually running python fetcher/fetcher.py after every gameweek, the scheduler runs it for you on a timer. You start it once, leave it running, and your data stays current automatically.

import sys, os

project_root = os.path.dirname(os.path.dirname(os.path.abspath(__file__)))
sys.path.insert(0, project_root)

from apscheduler.schedulers.blocking import BlockingScheduler
from fetcher.fetcher import fetch_all
from predictor.predictor import run_simulation

def daily_update():
    print("Starting daily update...")
    fetch_all()
    run_simulation()
    print("Daily update complete!")

scheduler = BlockingScheduler()
scheduler.add_job(daily_update, trigger="cron", hour=6, minute=0)

print("Scheduler running. Updates daily at 6:00 AM.")
scheduler.start()
LineCodeExplanation
1import sys, ossys gives us sys.path (where Python looks for modules). os gives us file path tools. Imported together on one line since both are needed for the path setup.
3os.path.abspath(__file__)__file__ is a special Python variable containing the path of the current file. abspath() converts it to a full absolute path (e.g., C:\...\scheduler\scheduler.py).
3os.path.dirname(...dirname(...))dirname() gets the parent folder of a path. One dirname() gives us the scheduler/ folder. Two nested dirnames() give us the project root (football_analytics/). We need the root to import our other modules.
4sys.path.insert(0, project_root)Adds the project root to Python's module search list at position 0 (highest priority). Now when we write "from fetcher.fetcher import fetch_all", Python knows to look in the project root for a folder called "fetcher".
6BlockingSchedulerA scheduler that "blocks" — meaning it keeps the script alive and running, waiting for the next job time. If you used BackgroundScheduler instead, the script would finish and exit immediately after setup.
9def daily_update():A regular Python function we define ourselves. The scheduler will call this function at 6am every day. It simply calls fetch_all() then run_simulation() in sequence.
14scheduler.add_job(..., trigger="cron", hour=6)Registers the daily_update function as a job. "cron" trigger means use cron-style scheduling (traditional Unix scheduler format). hour=6, minute=0 means "run at 06:00". Other options: trigger="interval", hours=1 would run every hour.
16scheduler.start()Starts the scheduler. This call never returns — the program sits here, waiting for the clock to reach 6am. When it does, daily_update() runs, then the scheduler waits again for the next day.

app/app.py

The Streamlit web dashboard — reads from MongoDB and displays everything in the browser

Purpose

This is the visual layer of the app. Streamlit turns Python code into a web page automatically — you never write HTML or CSS. Every time a user interacts (clicks a button, changes a filter), Streamlit re-runs the script from top to bottom and updates the page.

import streamlit as st
from pymongo import MongoClient
import pandas as pd
import plotly.express as px

st.set_page_config(
    page_title="Premier League Analytics",
    page_icon="⚽",
    layout="wide"
)

@st.cache_resource
def get_db():
    client = MongoClient(os.getenv("MONGO_URI", "mongodb://localhost:27017"))
    return client["football_analytics"]

db = get_db()
page = st.sidebar.radio("Go to", ["Standings", "Matches", "Top Scorers", "Predictions"])
LineCodeExplanation
1import streamlit as st"as st" creates an alias — instead of writing streamlit.title() every time, we write st.title(). This is a very common Python pattern for frequently-used libraries (pandas as pd, plotly.express as px).
3import pandas as pdPandas is imported as "pd" — universal convention. Pandas provides the DataFrame, which is Python's equivalent of an Excel spreadsheet: rows, columns, filtering, sorting, all in memory.

12@st.cache_resourceA decorator (the @ syntax). Decorators modify the function below them. @st.cache_resource tells Streamlit: "run this function once, cache the result, and reuse it on every subsequent call". Without this, a new database connection would be opened on every user interaction.
18st.sidebar.radio(...)Creates a set of radio buttons inside the left sidebar panel. The user clicks one option and "page" holds the selected string. Streamlit re-runs the whole script whenever a widget value changes, so the correct page content is shown automatically.

Predictions Page — key parts

pred_doc = db.predictions.find_one({}, {"_id": 0})
predictions = pred_doc["predictions"]
filtered = {k: v for k, v in predictions.items() if v > 0}
df = pd.DataFrame(list(filtered.items()), columns=["Team", "Win %"])

st.plotly_chart(fig, use_container_width=True)
cols = st.columns(3)

    with cols[i]:
        st.metric(label=row["Team"], value=f"{row['Win %']}%")
LineCodeExplanation
—db.predictions.find_one()find_one() returns a single document (or None). We only have one predictions document (we drop and recreate it each time), so this is all we need. More efficient than find() when you only expect one result.
—{k: v for k, v in predictions.items() if v > 0}A dictionary comprehension. predictions.items() gives (key, value) pairs. We rebuild the dict keeping only teams where the win probability v is greater than 0. This removes 15+ teams with 0% chance and makes the chart readable.
—list(filtered.items())items() on a dict gives pairs like [("Arsenal", 42.3), ("Man City", 38.1)]. list() materializes them. Passing this to pd.DataFrame with columns=["Team","Win %"] creates a two-column table.
—px.bar(df, x="Team", y="Win %", color="Win %", color_continuous_scale="RdYlGn")Creates a bar chart. x and y set the axes. color="Win %" colours each bar by its value. "RdYlGn" is a colorscale: low values are Red, medium Yellow, high Green — perfect for probability (low=red danger, high=green safe).
—st.columns(3)Splits the page into 3 equal-width columns. Returns a list of column objects. You use "with cols[i]:" to place content inside a specific column. Used here to show the top 3 teams side by side as a podium.
—enumerate(df.head(3).iterrows())head(3) takes first 3 rows. iterrows() loops row by row, yielding (index, row_data). enumerate() adds a counter i (0, 1, 2) so we can use it as a column index. The underscore _ is the row index which we don't need.
—with cols[i]:A context manager. "with" tells Python: "everything indented under this block belongs inside this column". st.metric() called inside the "with" block renders inside that column.
—st.metric(label=..., value=...)A Streamlit widget that displays a big highlighted number with a label above it — perfect for KPIs and key stats. Shows the team name as label and their win % as the big number.

How the pieces connect — the full picture

1. football-data.org → provides live Premier League JSON data via API
2. fetcher.py → downloads it and stores in MongoDB collections (standings, matches, scorers)
3. predictor.py → reads standings + remaining matches → simulates 10,000 seasons → stores % probabilities
4. scheduler.py → calls fetcher + predictor automatically every morning
5. app.py → reads all collections from MongoDB → renders tables and charts in Streamlit
6. Docker → runs MongoDB and the Python app in isolated containers, bypassing Windows restrictions
7. .env → keeps your API token secret and separate from code
